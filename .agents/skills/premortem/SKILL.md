# Pre-mortem

Представьте, что прошло 12 месяцев, вариант выполнен и провалился. Задача — объяснить, почему. Пре-мортем
даёт больше причин, чем вопрос «что может пойти не так?», но качество причин он сам не гарантирует. Поэтому
каждая причина проверяется на опору и превращается в сигнал, который можно отслеживать.

## Процедура

1. **Пять причин, разных по природе:** рынок (спрос, конкуренты, альтернативы), продукт (не решает задачу,
   не работает у части аудитории), экономика (затраты, выручка, окупаемость), исполнение (сроки, команда,
   зависимости), коммуникация (не поняли, не поверили, не заметили).
2. **Опора.** Причина, которая следует из данных, ссылается на строки реестра. Причина без опоры остаётся
   гипотезой: так и помечается, а проверка уходит в план.
3. **Конкретность.** «Риск потерять аудиторию» — не причина. Причина называет механизм и масштаб:
   «новые пользователи с одной из платформ не проходят настройку, потому что там нужно отдельное системное
   разрешение».
4. **Ранние сигналы.** Для каждой причины — индикатор, который покажет провал заранее, и где его смотреть.
   Самые сильные сигналы становятся kill-критериями варианта: сигнал, порог, дата.

## Чего не делать

- Не повторять одну причину в пяти формулировках.
- Не опираться на синтетику как на доказательство.
- Не смягчать причины для выбранного руководителем варианта: pre-mortem проводится одинаково для всех,
  включая «оставить как есть» и «закрыть».
